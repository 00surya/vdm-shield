# VMD Shield — engineering guide

This guide describes the implemented prototype, not a certified surveillance appliance. Operator instructions are available in the application's Help page in ten languages. Translations are drafts pending native-speaker review. UI controls remain English.

## Architecture and entry points
Flask serves the local MVC application. run.py starts the server; python -m vmd creates the app through the same factory. device.py starts a server and an installed Chromium/Chrome kiosk for an attached display. vmd/app.py defines the factory, access checks and response headers. Importing it does not start a source manager.
Controllers in vmd/controllers handle source, evidence, library and review requests. SourceManager in vmd/models/sources.py owns engine instances and the shared Store. Templates and local static JavaScript render the interface; no frontend build service or online translation is required.
The main navigation is Live view, Alerts, Recordings, and Device & settings. Advanced exposes setup, history, metrics, training and Help. Advanced is a navigation group, not a role-based access boundary.

## Capture and analysis pipeline
SourceSettings describes an upload or USB/HTTP/RTSP camera. Each Engine owns capture, pose/motion analysis, buffers and background workers. YOLO11n pose supplies person geometry; motion and temporal rules propose behavioral events. ZipDepth runs through ONNX Runtime CPU at a normal 1 FPS target. Per-person relative Z is 0 near to 1 far within one sampled frame, not metric distance or a persistent coordinate.
YOLO26s provides the exact 80 COCO classes as contextual detections. Its official v8.4.0 asset is checksum-pinned and its class ordering is checked. The specialist threat-yolov8n detector is separate; changing the COCO model does not upgrade weapon recognition. Check scripts/download_object_model.py and scripts/download_threat_model.py for their separate assets.
Depth and object inference run in background workers. Frames may be skipped to stay near live time. Browser display rate, camera input rate, pose/motion analysis rate and background worker rate are different measurements. Larger detectors require renewed full-pipeline hardware benchmarks.

## Camera persistence and recovery
Camera definitions are atomically saved to data/cameras.json with owner-only permissions. URLs can contain credentials; protect the filesystem and backups. Upload sessions are not restored. Enabled camera definitions restart with the server. Explicit Stop persists; Remove deletes the definition without deleting prior evidence.
The recovery worker checks every five seconds. Failed, idle, ended or stopping enabled sources, and streams stale for more than 15 seconds, are eligible for retry. Backoff grows and is capped at 300 seconds. Successful live operation resets the retry count. Engine shutdown can still wait for a model operation; this is not an OS-level watchdog.
A four-source process limit is a software bound, not a validated device capacity. Camera discovery, distributed device management and remote provisioning are not implemented.

## Events, evidence and retention
Store uses SQLite and a bounded background write queue. Incidents, telemetry, uploads, normal samples, reviews and settings are stored locally. Evidence uses bounded raw and annotated buffers; available pre-event footage may be shorter at startup or under memory limits. Raw clips are resized/compressed, not lossless originals. Following frames update the same event when available.
Alert review can confirm, dismiss, or correct a label. The detector proposal and operator correction remain distinguishable. Events move to History after 12 hours; that is a display filter rather than deletion. General objects provide context and do not independently generate weapon alerts.
Retention defaults to seven days and applies to new automatic evidence. Existing clips retain their expiry. Expiry removes evidence and playback cache but preserves event records; uploads and operator-uploaded training clips require manual removal. Continuous full-feed recording is not implemented.
Evidence health reports writer availability, queue depth, dropped records and last alert-clip save in the current service session. Writer readiness is not proof that all evidence is playable. Inspect encoding errors and verify playback. The last-save timestamp is session-local, not a persistent audit timestamp.

## Human review and partial-class learning
Human clip labels train the temporal event classifier, not YOLO or ZipDepth. Object-detector fine-tuning would require object annotations such as bounding boxes. The temporal model uses a frozen ResNet18 encoder and a trainable GRU head. Reviewed examples have higher weight; unreviewed model-generated alerts do not train themselves.
Training needs at least three distinct normal clips and two clips of an event class to build a candidate. These are software minimums, not enough evidence of deployment quality. Exact duplicates are removed and conflicting duplicates excluded. Re-encoded near-duplicates still need manual review. Source groups must reflect the original camera or footage.
A dataset with normal/fight clips cannot validate fall or weapon recognition. Keep historical reviewed examples to avoid forgetting. Unobserved classes must not be relabeled as normal. Pretrained detectors and heuristics remain active while the temporal head covers only its learned classes.

## Validation, activation and rollback
The source holdout requires at least 20 reviewed clips across three groups, with at least five normal and five event clips on the held-out source. Aggregate event recall must reach 80% and precision 60%. Replacement metrics must not regress against the active model on the same clean holdout. A validation source previously seen by the active model prevents that comparison.
The class-coverage gate additionally requires at least five held-out clips for each candidate class and 80% per-class recall. A candidate cannot drop an active class, and unsupported classes in the validation set block activation. This may require a larger and deliberately designed dataset than the aggregate gate alone suggests.
Candidates are saved separately from the active temporal_model.npz. Successful replacement retains temporal_previous.npz. File retention is not a one-click rollback workflow. Do not change checkpoint files while inference is running. Keep an independent final test set; repeated selection against a small holdout can overfit.
Model scores are uncalibrated. The classifier has no calibrated unknown-scene rejection system. “Normal” can therefore be wrong for an unseen event. Validate exact event labels, false alerts per camera-hour, missed events and detection delay, not only binary event accuracy.

## Fusion behavior and intended improvements
Current fusion is additive rather than a calibrated ensemble. Pose/motion heuristics and specialist threat alerts remain active. Fresh temporal predictions can add reviewable events subject to score and cooldown gates; a normal prediction does not cancel a heuristic or weapon alert. General COCO detections remain contextual.
A future fusion layer should align camera, person and time, retain signal provenance, and learn class-specific decisions on independently reviewed data. Do not average heuristic scores and model confidence as interchangeable probabilities. Compare each component alone and their combination. Deploy only when measurements improve; more time or more labels alone does not imply improvement.

## Device status and internal sizing
Device status excludes uploaded videos from the camera count and reports connectivity, observed processing rate, worker state, storage and service uptime. On pace uses 90% of the requested rate, limited by measured input rate. This threshold measures processing speed, not detection quality. Low storage means less than 10% or 5 GB free; the entire data filesystem is measured.
Set VMD_INTERNAL_TOOLS=1 only on internal installations to enable sizing. The API is disabled otherwise. data/validated_devices.json supplies tested profiles: name, specifications, validated, tested_cameras, minimum_camera_fps, resolution, pipeline, benchmark_date and report.
Sizing matches requested FPS, resolution and pipeline to validated concurrent-camera results. It estimates multiple-device count from those results; it does not coordinate the devices. No validated hardware profiles ship with the project. Collect sustained, representative benchmarks with all workers, thermal conditions and evidence writing before making customer commitments.

## Security and deployment
The server binds to loopback and checks Host, Origin and the custom mutation header. Run .venv/bin/python scripts/provision_access.py to configure the operator password. A salted password hash is stored in data/access.hash; restart to activate it. With provisioning, pages, media and APIs require the operator account through HTTP Basic authentication.
Without a provisioned password the application remains a local development instance. There are no separate operator/admin roles, session logout, remote TLS service or enterprise identity integration. Browser Basic credentials can remain cached; close the browser session when handing over the device. Do not expose the local HTTP server to a network.
For display use, connect HDMI and a mouse/keyboard or supported touchscreen. Standard TV remotes are not supported. deploy/vmd-kiosk.desktop.example is a Linux desktop-autostart template, not installed OS configuration. Set absolute paths on the target image. Automatic graphical login, service supervision, signed updates, disk protection and recovery after power loss require deployment engineering.
VMD_DEVICE_NAME and VMD_SUPPORT_CONTACT configure product information. Version is read from package metadata. Update status honestly reports that managed updates are unconfigured. Review third-party model licensing before commercial distribution.

## Testing and maintenance
Run .venv/bin/python -m pytest -q for the automated suite. Relevant tests cover source recovery, password protection, internal sizing, APIs, event history, training and class-coverage gating. Unit and API tests do not establish camera compatibility, sustained FPS, real-world accuracy or rendered layout quality.
Before changing detectors, verify official weights, checksum, exact class mapping and inference, then benchmark representative streams. Before destructive data cleanup, stop all writers and inference processes. Removing training data does not erase information from existing trained checkpoints; handle derived checkpoints deliberately.
Before delivery, test power cycling, reconnects, storage exhaustion, evidence playback, credential provisioning, shift handover, UI scaling and translated instructions with actual operators. Keep deployment acceptance records tied to hardware, software, models and pipeline settings.

## Frame identity and measured pipeline telemetry
Capture assigns a unique connection session, monotonically increasing frame ID, source timestamp, elapsed stream time, wall-clock capture time and monotonic capture time. File timestamps prefer decoder presentation times with a nominal-FPS fallback when unavailable. Workers preserve identity through result delivery; capture-to-result latency uses monotonic time. Frame identities do not survive as a global sequence across reconnects; the session is part of the key.
Routine background submissions originate from capture, independently of the pose loop. Existing event-frame priority can request an exact frame. Queue capacity remains bounded. Object and weapon inference still share a process and are reported together; separate model throughput and classifier throughput are not reported.
A compressed raw capture buffer retains up to 20 seconds or 64 MiB per source, whichever limit is reached first. Delayed weapon events select that buffer around source time and include the detector's exact raw and annotated frame. Late results retain their original identity; they are not treated as boxes for the latest pose frame. Extremely late results may lack surrounding footage if it has already left the buffer. This is not lossless or continuous recording.
Analytics includes current per-source input, pose/motion, depth and combined object/weapon rates, processing time, capture-to-result delay, result age and evidence queue counters. Worker rates use a rolling 10-second completion window. Unavailable measurements display a dash. These are operational measurements, not validated accuracy, detection guarantees or long-term latency percentiles. Browser display rate is not part of these server measurements.
